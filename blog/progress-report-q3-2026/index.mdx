## AI Usage Policy

The OpenGOAL project has some strict rules regarding AI usage with regards to contributions:

### General Rules / Etiquette

- **All AI usage in any form must be disclosed.** You must state the tool you used (e.g. Claude Code, Cursor, Amp) along with the extent that the work was AI-assisted.
- **No commits authored/co-authored by AI agents will be merged.** We currently have no commits in `master` that are associated with Claude, Copilot, etc., and we would like to keep it that way.  The least you can do when making a contribution is making the commits yourself.
- The following rules can be summarized with the new term of [don't be a meat proxy](https://dontbeameatproxy.com/):
  - **The human-in-the-loop must fully understand all code.** If you can't explain what your changes do and how they interact with the greater system without the aid of AI tools, do not contribute to this project.
  - **Issues and PR discussions can use AI assistance but must have a full human-in-the-loop.** This means that any content generated with AI must have been reviewed and edited by a human before submission. AI is very good at being overly verbose and including noise that distracts from the main point. **Humans must do their research and trim this down.**
- **No AI-generated media is allowed (art, images, videos, audio, etc.).** Text and code are the only acceptable AI-generated content, per the other rules in this policy.
- **Bad AI drivers will be denounced.** People who produce bad contributions that are clearly AI (slop) will have future contributions blocked, we don't have time or the motivation to deal with this. Additionally, this block list will be public and may be used by other projects to be aware of bad actors. We love to help junior developers learn and grow, but if you're interested in that then don't use AI, and we'll help you. I'm sorry that bad AI drivers have ruined this for you.

### OpenGOAL / Decompilation Project Specific Rules

- **No large or significant contributions to `/goal_src/` (the actual decompiled game code) from new contributors.** Sorry to gatekeep, but there are several reasons for this:
  1. We successfully finished decompiling Jak 1, Jak 2, and Jak 3 without AI assistance, there is no reason to reach for an LLM for the last game (Jak X) when our decompilation tools are already heavily mature.  We would like to be able to say that all four games were decompiled the traditional way, especially since projects like these work via very loose legal gray areas / precedents for reverse-engineering.  It is anyone's guess at this point what will happen to all of these new AI-powered decompilation projects in the near-future and we have no reason to risk it after how successful and careful we have been.
  2. The goal of our project is not to just get the games running on PC, as so many recent decompilation projects have as their only focus.  Our goal is to understand the game's code and to clean it up as we go along so it can be easily modified, extended, and read by humans.  This cannot be done using LLMs by someone who does not have the hard-earned experience of actually working with GOAL code.
  3. Changes to this code can easily cause new bugs for users, bugs that we have no interest in solving, nor do we want to cause an inconvenience for our existing users.
- **No Android/Mobile support related contributions.** No one on the team is interested in being involved in the Android or other mobile ecosystems, maintaining that release/distribution process, etc.  If you really want to do this, feel free to fork the project, we are not interested in it.
- **No LLM powered translations.** We have already seen the low quality outputs of AI assisted localization, with people having to comb through and fix obvious mistakes that were never proof-read.  We are taking the stance that no translations are better than bad machine translations.  They also put up the false impression that the translations are complete, potentially discouraging or making it harder for actual translators to make an informed contribution.  Once again if you really want to do this, feel free to fork and distribute the translations yourself.
- **No massive refactors or additions to enable low percentage user base support**.  Examples would include a Metal or DirectX renderer.  These sorts of things are large undertakings and come with significant maintenance burden, while only making an impact for 0-1% of our user base.  History shows that unfortunately these sorts of contributions are not made by people that will assist long-term with fixing bugs, but even if they were to break the mold and fix every bug that users report, it really isn't worth the noise.  Since the beginning we have made the decision to not support every possible user to improve the developer experience, for example, requiring things like AVX support and a modern OpenGL version, we are sticking by this decision.

  Every discussion, issue, and pull request is read and reviewed by humans (and sometimes machines, too). It is a boundary point at which people interact with each other and the work done. It is rude and disrespectful to approach this boundary with low-effort, unqualified work, since it puts the burden of validation on the maintainer.

## Launcher

### Restore external links on mod pages <PRLink href="https://github.com/open-goal/launcher/pull/1023"/>

Added back the icon to jump to a mod's website/README.

### Add swap space metric to support package <PRLink href="https://github.com/open-goal/launcher/pull/1072"/>

Some Linux users have reported `Decompiler process terminated by signal 9`, which can result from the decompiler using all the RAM and swap space. Allocating more swap space results in the decompiler finishing successfully. This change added information to the support package to help identify this issue.

### Hide (vanilla) tooling update icon while on mod page <PRLink href="https://github.com/open-goal/launcher/pull/1032"/>

The launcher header shows either the currently installed version of the vanilla tooling, or the version of a particuar mod if you're on the mod's page. There is also an icon that appears in the header when there's a vanilla tooling update, but it was still showing from mod pages, causing confusion. Now it only shows while the vanilla tooling version is shown.

### Add VSCode debug adapter support <PRLink href="https://github.com/open-goal/jak-project/pull/4365"/> <PRLink href="https://github.com/open-goal/opengoal-vscode/pull/375"/>

Added a debug server to goalc that sends JSON over the socket to communicate with an external debugger using the Debug Adapter Protocol. This lets us debug GOAL code in a proper debugger with breakpoints, step over, step in and step out per line, stack frames and supports watches for global symbols, registers and local variables (local variables only work within the most recent stack frame).

Watches that track addresses holding a reference type generate a list of field names according to the object's type. All fields will show their name, type and value and, depending on the type, will try to infer extra info like symbol names/values, function names for function fields, enum values and more.

### Various GLTF exporter fixes <PRLink href="https://github.com/open-goal/jak-project/pull/4371"/>

- Merc and TIE envmaps now properly extract
- Changed joint offset in convert_per_vertex_data since we now export the align bone
- The bone accessor for merc models now uses TINYGLTF_COMPONENT_TYPE_UNSIGNED_BYTE, fixing a decompiler crash when attempting to reimport an extracted model into the game without first importing it into Blender and re-exporting
- All model buffers now get merged into one large buffer before export, saving some space and increasing parsing speed of GLB files
- Tfrags, TIEs and shrubs are now no longer stored in one giant mesh per tree and get grouped into categories:
  - Tfrags will be grouped by the tfrag tree name they come from (normal, trans, dirt, ice, etc.) and get separated by the texture their material uses (tfrags are not instanced, so this is the next best solution)
  - TIEs and shrubs get grouped by tree index and separated by their proto name (TIE wind will also be grouped separately)

## Jak 1

### Patched debug crash in subtitle code <PRLink href="https://github.com/open-goal/jak-project/pull/4348"/>

Fixed a crash in subtitle code that only runs in debug mode, and tries to log information about any currently playing cutscene. The code was checking the handle `(-> *art-control* spool-lock)` rather than the process `(handle->process (-> *art-control* spool-lock))` to decide whether or not to log. While the handle may not be `#f`, this might still not resolve to a valid process, in which case the game crashes trying to log the cutscene information.

### Patched autosave/progress locked menu <PRLink href="https://github.com/open-goal/jak-project/pull/4340"/>

There's an original game bug where under the right conditions, you can get stuck on a blank pause menu screen permanently, and have no choice but to reboot the game.

The first time you collect a cell after saving to a new file, the game will show a popup telling you about the autosave feature. If you collect such a cell during a pause buffer (the brief window after pressing Start and L2/R2 on same frame), the game gets stuck waiting on conditions that will never change. 

The pause menu is waiting on the autosave to finish, but the autosave is stuck waiting on the cell cutscene to play, and the cell cutscene is stuck waiting to play because the pause menu has come up. The game is actually still running, it just has no way to get unblocked and ignores any player input (its unblocked by running code in the REPL in the video below).

This isn't a bug most players would run into, but it does affect speedrunners in certain situations. So we opted to fix this bug only while speedrun mode was enabled. In speedrun mode we were already skipping the autosave popup, but not until after the code that loops until there's no pending cutscene was satisfied. We changed the order of these checks, so that we wouldn't bother with the cutscene check if we were in speedrun mode.

### Restored NaN check in nav code <PRLink href="https://github.com/open-goal/jak-project/pull/4359"/>

Added back a NaN check in some common nav code which was inadvertently removed during decompiler cleanup. This was causing enemies to suddenly disappear in certain situations.
